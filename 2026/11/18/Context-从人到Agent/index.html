Context：从人与人到 Agent 与 Agent

Joie2026-11-182026-11-18

两个后端工程师对齐一次发布，全程四句话。

换成两个 Agent 做同样的事，交接文档写了三页，协议也定义清楚了，结果还是漏掉了”上次事故之后不许再动那个索引”。

这不是 Agent 笨。是 context 的形状变了——这句话不是修辞：人之间的 context 长在一个共享的世界里，Agent 之间的 context 长在协议里，而协议只装得下被显式写出来的那部分。

要谈清楚这件事，得先把两个常被混用的词分开。

一、先分清”有什么”和”怎么处理”

聊 context 最大的混乱，是把组成项和加工手段并列着说。像”记忆、知识、摘要、检索、任务状态”这样排成一串，看起来是一类东西，其实前三个是名词（context 里有什么），后两个是动词（对这些东西做了什么）。

  flowchart TB
    C["Context"] --> A["组成项：里面有什么"]
    C --> B["加工手段：对它做了什么"]
    A --> A1["记忆"]
    A --> A2["知识（含经蒸馏得到的结论）"]
    A --> A3["任务状态"]
    A --> A4["对话历史"]
    B --> B1["蒸馏：产物搬到知识或记忆里"]
    B --> B2["摘要：产物留在原位，且会被再摘要"]
    B --> B3["检索：不生产内容，只决定当下可见"]
    B --> B4["裁剪：纯丢弃，不新增任何信息"]

四个组成项，按”密度”从高到低排：记忆是长期沉淀的事实与偏好，一条能顶一千字；知识是可以被查的资料与规范，量大但需要定位；任务状态是目标、进度、约束和验收标准，通常只有几句话，却决定了所有动作对不对；对话历史是这一路说过的话和工具返回，体积最大、密度最低。

四个加工手段，差别在”产物落在哪”：

  • 蒸馏是从大量上下文里提炼高价值结论。它的产物不应该留在原地，而应该搬进知识或记忆——所以严格说，蒸馏产出的不是”context 的一部分”，而是新的知识条目，我在后文一律标注”经蒸馏得到”。
  • 摘要是等比例压缩：保留骨架，丢掉细节，产物留在原位继续参与下一轮。这意味着摘要会被再次摘要，误差是累积的。
  • 检索不生产任何内容，它只改变”此刻哪些东西是可见的”。检索不到，等于不存在。
  • 裁剪是纯粹丢弃：截断、滑窗、丢掉低分块。它不新增信息，只是把成本压到预算内。

把这两类分开之后，三个层次就能用同一套语言描述：每一层的 context 由哪几个组成项承担、靠什么通道传递、在哪一步失真。

二、人与人：共享经历是免费的带宽

组成。 两个老同事之间，真正在起作用的东西比说出口的多得多：

  • 记忆：一起做过的项目、上次踩的坑、对方的工作习惯
  • 知识：同一个领域的隐含假设——“灰度”是什么意思，不用说
  • 任务状态：当前发布到哪一步、谁在等谁
  • 对话历史：这次对话说过的话（占比其实最小）
  • 还有一项不好命名但确实存在：关系与默契，也就是”哪些话不用说完”

传递。 通道是语言，但真正的带宽来自共享环境：同一个代码库、同一块白板、同一份排期表。这些是免费的共享存储，不需要谁去同步。

于是四句话就够了：

“周五发，灰度 5%，出问题回滚到上个 tag，别动那个索引。”

这句话里，”灰度 5%”是知识（团队惯例），”别动那个索引”是记忆（上次事故的结论），”周五发”是任务状态，而”回滚到上个 tag”是共享知识里的操作路径。换个新人来听，同一句话会漏掉一半——不是听不懂字，是缺了那层共同经历。

失真。 人-人这一层的损耗很有特点：

  • 知识诅咒：默认对方知道。省掉的前提，恰恰是最关键的那部分。
  • 记忆重构：两个人对同一次会议的复述会不一样，而且都觉得自己是对的。
  • 省略号：”老规矩”这种说法，在共享语境里是高效压缩，在语境断裂时就是信息黑洞。

加工手段。 人脑一直在做摘要和检索——记住结论、忘掉过程，用旧经验类比新问题。注意这些是手段：它们的产物（”我记得上次是这么解决的”）落在记忆里，而不是”摘要”里。

三、人-Agent：显式输入，漏掉的补不回来

组成。 跟 Agent 说话时，起作用的是这五样：

组成项 在人-Agent 里具体是什么
记忆 跨会话留下的偏好与事实（”这个仓库用 pnpm”）
知识 检索进来的文档、代码、规范；含经蒸馏得到的结论
任务状态 目标、待办、当前改到哪个文件、验收标准
对话历史 本轮说过的话，以及工具返回的原文
系统提示 角色、边界、输出格式——它是规则，不是知识

传递。 通道窄且单一：文本 token。工具返回值、文件系统、结构化参数是它的几种变形，但本质上都得变成 token 才能进窗口。

  flowchart LR
    S["系统提示<br/>角色与规则"] --> W["上下文窗口"]
    H["对话历史"] --> W
    R["检索到的知识"] --> W
    M["记忆"] --> W
    T["任务状态<br/>目标 · 约束 · 验收"] --> W
    W --> L["模型"]
    L --> ACT["工具调用 / 动作"]
    ACT --> T
    ACT --> H

失真。 这一层有五种典型损耗，而且大多是单向的：Agent 不会追问你没说的东西，它只会猜。

  1. 意图说不全。 人说话默认省略，Agent 没有共享语境来补全。
  2. 窗口有限。 上下文满了就要压缩，压缩是有损的，而且会反复发生。
  3. 检索错位。 召回不相关的内容会污染判断，漏召回则让 Agent 凭空发挥。
  4. 注意力稀释。 上下文越长，中段信息的权重越低——重要的约束写在第 3 段，往往不如写在最后一段管用。
  5. 软约束丢失。 “别改接口”到底是别改签名，还是别改返回结构？自然语言里的边界是模糊的。

一个具体例子：让 Agent 修”登录偶发失败”。如果你只给这一句，缺的是任务状态里的三样东西——复现路径、验收标准、以及约束（不许改表结构）。Agent 会自己编一条复现路径，改完说”已修复”，而你无法验证。

加工手段。 这一层是四种手段最密集的地方：

  • 蒸馏：一轮任务跑完，把三十轮对话压成五条决策，写进项目知识——产物搬家，标注”经蒸馏得到”。
  • 摘要：窗口快满时把前二十轮压成一段，留在原位。它会随下一次压缩再被摘要。
  • 检索：RAG、记忆召回、按需读文件。决定”当下可见”，不改变存储。
  • 裁剪：丢掉长尾的工具输出、滑动窗口。便宜，但不可逆。

四、Agent-Agent：协议与结构化状态

组成。 两个 Agent 之间，能共享的东西必须被显式建模：

组成项 在 Agent-Agent 里长什么样
记忆 各自的私有记忆；共享的部分要有命名空间和读写权限
知识 共享知识库，或通过工具按需检索
任务状态 任务对象：id、目标、约束、验收、依赖、状态机
对话历史 消息流或事件日志，通常只传摘要
协议契约 工具 schema、消息格式、错误码——这一层独有的组成项

传递。 通道是协议：JSON-RPC、HTTP、事件总线、共享存储、文件系统。每一条都要定义格式、版本和错误处理。

  sequenceDiagram
    participant P as 主管 Agent
    participant B as 共享任务板
    participant W as Worker Agent
    P->>B: 写入任务（目标 / 约束 / 验收）
    P->>W: 只发一句指令 + 任务 id
    Note over W: 看不到"为什么这么做"<br/>也看不到历史上的失败尝试
    W->>B: 读取任务
    B-->>W: 目标与验收在，约束字段没人填
    W->>P: 交付结果（口径与主管预期不一致）

失真。 Agent-Agent 的失真最隐蔽，因为它发生在”格式正确但语义丢失”的地方：

  1. 只传 what，不传 why。 结构化字段能表达”做什么”，很难表达”为什么不能那样做”。
  2. 状态断链。 对方的上下文不共享，同样的推理要重来一遍，还可能推出不同结论。
  3. schema 装不下软约束。 “尽量别动公共模块”没法写成必填字段。
  4. 幂等与重试。 消息重发、任务重跑时，副作用可能发生两次。
  5. 信任错位。 下游把上游的输出当事实，而上游的输出其实是它的推断。
  6. 版本漂移。 工具或 schema 升级了，对端不知道。

上面那张时序图就是最常见的坑：任务板上写着”约束”，但派活时只发了一句指令，Worker 根本不会去读那个字段——上下文不是”存了就有”，是”传了才有”。

加工手段。 这一层的主战场是交接：把上下文蒸馏成交接摘要（而非全量转发）、按需检索对方的知识、裁剪只传必要字段。结构化本身也是一种加工——把自然语言里的意图压成字段，压的过程一定会丢东西，问题只在于丢的是不是关键。

五、三层放在一起看

维度 人与人 人-Agent Agent-Agent
带宽 高（语言 + 共享环境 + 非语言） 中（文本 token 单向） 低（结构化消息）
共享成本 几乎为零，是共事的副产品 需要显式写提示、建记忆 需要设计协议、schema、状态存储
保真度 高（隐含共享补全了省略） 中（漏了就是漏了） 最低（格式对、语义丢）
主要失真 知识诅咒、记忆重构 意图不全、压缩有损、检索错位 只传 what 不传 why、状态断链
加工手段的主战场 摘要与类比（产物进记忆） 蒸馏、摘要、检索、裁剪全都用 交接蒸馏、按需检索、字段裁剪 
  flowchart LR
    L1["人与人<br/>共享经历<br/>成本≈0 · 保真高"] -->|"把隐含的东西写出来"| L2["人-Agent<br/>显式输入 + 记忆<br/>成本中 · 保真中"]
    L2 -->|"把写出来的东西建模成协议"| L3["Agent-Agent<br/>协议 + 结构化状态<br/>成本高 · 保真低"]
    L3 -.->|"想找回保真度<br/>只能补共享状态"| L4["共享任务对象 / 共享知识 / 事件日志"]

三层之间真正的递进，不是”对象变了”，而是共享成本从免费变成必须显式建设，而保真度反而在下降。

原因很简单：人-人这一层，大量 context 是环境的副产品——你们在同一间会议室、同一个代码库、同一段经历里，不需要谁去同步。到了 Agent-Agent，这种副产品彻底消失，只剩协议能传的东西；而协议只装得下被结构化的部分，结构化的过程本身就是一次有损压缩。

所以 Agent 协作里最贵的不是模型，是把隐含知识显式化的那部分工作量。

六、一句话的趋势判断

这几年”context 工程”的重心，正在从怎么把更多东西塞进窗口，转向怎么把该共享的东西结构化地放在窗口之外——窗口是工作台，不是仓库；记忆、知识、任务状态都应该有自己的位置，而 context 只负责在正确的时刻，把正确的那一小块端上来。
